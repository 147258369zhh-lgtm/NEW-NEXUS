# 运行、审批、会议协作与消息排版盘点（2026-11-15）

本轮用户明确授权修复“列表可打开，但运行中点击其他记录无响应”。运行模式、审批权限、会议组合与排版先审查并提出方案，等用户决定后再改；本轮不据此修改权限策略、会议流程或前端设计。

## 一、会话切换故障的定位

会话和会议列表标题都使用共享 `paneDragSource`，父行另有点击打开记录的回调。Compose Foundation 1.12.0 的默认触摸拖拽起手检测会消费短点的按下/抬起事件，标题作为子节点先接收事件，父行因而无法完成点击。它不限于运行中发生，运行时使用列表切换更容易感受到。

状态层本来支持多个会话运行，运行结果按 runId 和 conversationId 归属；修复不应取消后台任务或用“先停止”绕开问题。本轮目标是正确区分短点打开记录与中部长按拖动，保留原拖动视觉、排序及目录行为。实际修改、最小验证和交付记录附后。

## 二、NEXA 三种运行模式

| 模式 | 当前真实行为 | 边界 |
|---|---|---|
| 普通会话（默认） | 正常回答，按任务和工具授权执行 | 不等于只聊天，也不等于完全访问 |
| 计划 | 只读调研，并可管理计划、目标和记事本草稿 | 执行门禁阻止项目写入、终端、GUI和MCP；完全访问也不会解除计划模式限制。计划写完不自动转执行 |
| 目标 | 增加目标相关指令和运行标记，权限沿当前审批模式 | 选中目标不会自动创建持久目标；需要实际调用目标管理创建、启动。开始、恢复及增加预算另需本机确认 |

模式按会话保存并随消息传给运行器。切换模式不应被理解为重写已经启动的 Run。目标持久化、预算和恢复是另一条生命周期链，不能仅凭选中“目标”就宣称会持续自主执行到完成。

会议请求使用独立的主持人/参与者运行类型，目前没有完整复用会话的普通/计划/目标选择；但工具执行共用全局审批策略，并受每个成员角色的工具白名单及阶段限制。

## 三、NEXA 三种审批权限

默认是智能审批，设置是全局的，工具执行前重新读取；它与会话运行模式是两条独立维度。下表按当前实际通用工具策略记录，不按菜单名称推测：

这也意味着在一个会话中调整审批设置，其他后台会话/会议的后续工具调用也可能受影响；当前不是每个会话独立冻结的审批档位。仅切换查看记录不会主动改变审批设置。

| 操作 | 完全访问 | 智能审批 | 手动审批 |
|---|---|---|---|
| 普通读取、Root读取 | 自动 | 自动 | 自动 |
| 非Root的普通文件写入、复制、移动、建目录 | 自动 | 自动 | 自动 |
| 点击、输入、启动App、普通浏览器操作 | 自动 | 自动 | 自动 |
| 终端、删除、未知外部工具、MCP工具 | 自动 | 确认 | 确认 |
| Root身份文件写入 | 自动 | 确认 | 确认 |
| 被现有资金关键词规则识别的非读取操作 | 确认 | 确认 | 确认 |

完全访问不会替用户取得Android/Root授权，也不会打开已关闭的工具。资金判断目前依赖工具名和参数关键词，READ类别又先行自动放行；不能把该实现说成任意资金动作都已经得到完整语义识别和强制拦截。

### 必须单独说明的不一致

1. **手动审批并未实现菜单承诺的“写入先确认”。** 通用门禁将智能和手动放在同一分支，普通写入和GUI仍自动执行；菜单与权限健康页的说明本身也不一致。
2. **应用设置的确认类型存在独立门禁缺口。** `eta_control` 的执行/撤销交由设置控制链单独审批，手动模式仅检查 WRITE，却没有包含互斥的 CONFIRM 类型。权限模式切换本身是 CONFIRM，默认未额外限制本地Agent设置授权时，静态调用链允许未经确认切换为完全访问；清空记忆等确认类操作也受影响。这是源码可达证据，未在手机上尝试提权或删除。
3. 目标相关提示词对“完成需确认”的描述与当前执行器并不完全一致，不能以提示词替代真正的门禁。

上述问题本轮只记录，不擅自选择新的审批语义。建议下一轮先确定三种权限的准确合同，再统一所有工具和应用设置入口，尤其禁止模型绕过用户给自身提升审批权限。

## 四、Codex实际工作方式与对照

本次直接访问OpenAI开发者文档站返回403，改经GitHub API读取OpenAI官方公开仓库；结论固定到2026-11-14的提交 `81b995a6c9a4c978f399775cfa5ce50702368749`。同时本机 `codex --help` 核对了执行范围和审批开关。公开代码不能证明本机桌面每项实验功能均已开放，不将网页片段或未打开的文档链接当作证据。

**完全访问、请求批准、计划模式不属于同一组三选一。** 前两者关乎权限范围及审批安排，计划模式控制本轮如何工作。Codex还提供“代我批准”，与“请求批准”的主要差别是审批人。

| Codex权限安排 | 执行范围 | 谁批准需要确认的动作 |
|---|---|---|
| 请求批准 | 默认工作区权限；工作区外写入、网络等受相应边界约束 | 用户 |
| 代我批准 | 与请求批准使用同一工作区权限预设，不直接改成完全访问 | 独立风险审查子代理，功能是否可用受版本和管理设置影响 |
| 完全访问 | 使用取消该权限配置限制的预设，允许工作区外和网络访问 | 通常不逐条请求审批；其他规则及强制人工要求仍可生效 |

普通操作在已允许范围内可直接执行，“请求批准”不是每个工具调用都问。执行层结合命令规则、风险判断和所需范围决定是否请求，批准可限定单次、当前会话或适用规则。拒绝后返回模型寻找其他办法。`never`只表示不请求批准，不表示一旦受限就自动取得更高权限；如果仍有其他边界，失败会直接返回。

Codex还有只读、默认工作区读写、完全访问等底层范围预设。不能将“三种范围预设”“审批人选择”“计划模式”混成一套固定的三种运行模式。

Codex的计划模式会读取项目、查明事实、澄清关键取舍、输出可直接实施的方案，禁止实施性修改；可进行不修改受版本管理源码的检查、测试或构建。写完计划不会自行切成实施，进度清单工具也不会开启或退出计划模式。

```text
用户任务 + 协作方式 + 权限/审批安排
                     ↓
               模型提出工具调用
                     ↓
        执行层核对范围、命令规则和审批要求
                     ↓
         直接允许 / 交用户 / 交独立审查代理 / 拒绝
                     ↓
               在获准范围内执行
                     ↓
             真实结果返回模型，继续推进
```

| 对照点 | NEXA当前实现 | Codex公开实现 |
|---|---|---|
| 计划 | 工具效果类别硬门禁；终端与MCP整体禁用 | 协作指令禁止实施，可允许不改源码的检查命令 |
| 智能/代为审批 | 智能审批主要依据固定操作类别选择自动或人工确认 | 代我批准由独立审查子代理评估，不只是调低确认阈值 |
| 手动/请求审批 | 目前与智能通用门禁相同，且有CONFIRM误放行缺口 | 请求批准把需要审批的动作交给用户 |
| 完全访问 | 在Android授权、Root可用性、工具开关及角色权限内自动执行；有资金关键词确认 | 范围与审批组合的预设，仍受更高层规则及强制要求限制 |
| 目标 | 持久任务状态、预算、完成条件和恢复的独立链路 | 不能与权限档位对应；长期目标与协作/权限应分开理解 |

用户“未经同意不得更改UI”的项目规则不因完全访问而失效。权限能力表示程序能做什么，不代替具体任务授权。

供用户决定的整改方向：

1. 先修手动审批与确认类型缺口；权限提升、敏感授权和破坏性设置应有不能被同一模型自行跳过的用户确认。
2. 明确定义智能审批是“固定风险分级”还是“独立审查代理”，不要只沿用一个名称却没有对应机制。若引入审查代理，也不能替代必须由用户完成的确认。
3. 确定审批设置作用于全局、当前会话/会议还是当前运行；一次确认与可复用授权需要明确范围、撤销和有效期。
4. 计划模式允许什么，应由可证的只读能力界定；目标模式则需明确何时建目标、预算、完成条件、暂停和恢复，避免只有模式标签。

本轮上述四项均未实施，不把研究建议当成用户已批准的产品改动。

## 五、会议组合的真实现状

当前三种组合仅在创建时预填角色、主持人和名称，没有配置独立编排、共享范围或专门的场景提示词。按未被用户覆盖的内置角色：

| 组合 | 主持人 | 默认实际工作成员 |
|---|---|---|
| 方案讨论 | 规划角色 | 探索角色 |
| 资料研究 | 探索角色 | 规划角色 |
| 交叉审查 | 规划角色 | 编程角色、探索角色 |

主持人不计入工作成员，主要规划和汇总；规划、汇总阶段工具关闭，执行成员在工作阶段按角色授权使用工具。因此目前“方案讨论”并不是多个模型平等公开讨论。

一般流程：

```text
用户任务
   ↓
主持人规划分工（不使用工具）
   ↓
成员A独立执行 ─┬─ 成员B独立执行 ─┬─ 其他被调度成员
               ↓                  ↓
             主持人收集本轮结果与失败信息
                         ↓
                   可选汇总后给用户
```

直接@单个成员可跳过主持人分工；@多个成员可并行处理同一请求。界面同屏显示所有消息，不等于各模型共享同一份上下文。

成员按独立会话保存上下文；从公共历史重建时，只收明确@自己的旧用户消息和自身旧结果，不自动收其他成员结果或主持人旧汇总。主持人重建时收用户历史和自身汇总，本轮汇总时收到全体本轮结果；其持久上下文快照也可能保有此前已收到的材料。不能说主持人永远只见摘要。

当前没有全员互看、分阶段共享、私信、匿名或辩论轮次开关。成员可能共享附件、项目、文件和记忆资源，模型输入隔离不等于资源权限隔离或保密保证。

### 建议增加的用途与编排

| 用途 | 执行方式 | 信息可见范围 | 当前支持程度 |
|---|---|---|---|
| 方案讨论/头脑风暴 | 每人首轮发言，再接续、反驳、主持人归纳选项 | 公共发言全员可见，内部思考不共享 | 需新增共享上下文与多轮调度 |
| 资料研究 | 分渠道独立收集，汇总证据，再定向核验冲突 | 收集阶段独立，核验阶段共享相关材料 | 独立收集可做，阶段核验需补 |
| 交叉审查 | 先独立审查，再把意见交给另一个审查者复核 | 初审独立，互审时共享指定结果 | 当前可独立审查，缺真正互审阶段 |
| 多模型竞答/事实核验 | 相同问题独立作答，主持人对照证据与分歧 | 首轮互不看答案，最终比较后公开 | 可通过现有独立执行近似 |
| 方案实施 | 规划→实现→验证→退回修正 | 后阶段读取前阶段的指定成果 | 需顺序依赖、验收和返工编排 |
| 故障会诊 | 多专业先各自诊断，再集中质询争议 | 首轮独立，质询时公开相关证据 | 第一阶段可做，交叉质询需补 |
| 写作与审校 | 作者起草→编辑润色→事实审校→定稿 | 草稿与修改意见逐阶段交接 | 可手动多轮近似，自动流水需补 |
| 正反辩论/红蓝对抗 | 设定立场、轮流回应、裁判汇总 | 角色私有任务，论点按轮次公开 | 需轮次、定向投递和停止条件 |
| 专家共识/德尔菲 | 独立意见→匿名汇总→重新评价 | 初始独立，仅共享匿名聚合材料 | 需匿名、投票与收敛流程 |

建议区分“角色组合”和“协作方式”。用户选择用途后，系统套用相应的角色、执行阶段和可见范围；仅增加组合名称不会得到真正的公开讨论或交叉审查。这里的“公开”仅指成员可见的对外回复、工具结论和允许共享的材料，不要求暴露模型内部思考。

## 六、会话和会议排版由谁决定

**内容结构由模型生成，提示词约束表达，最终外观由软件统一渲染。**

- 模型决定使用哪些标题、列表、表格、代码或公式，以及具体文字。
- 现有全局提示词已经要求合法且克制的GFM、普通段落优先，必要时才用标题/列表/表格，表格逐行并前后留空行。
- 会话与会议共用消息组件、Markdown解析和样式，字体、字号、行距、颜色、表格边框、代码卡等由应用决定。模型不能直接把原生界面任意改成自己的样式。
- 普通回复没有再调用第二个模型统一排版；大体保留原文，只做显示解析及流式快照的临时闭合。角色改写和消息处理插件属于另行触发的路径，不是默认排版器。

| 格式 | 当前边界 |
|---|---|
| 标题、列表、引用、粗斜体、删除线 | 支持；六级标题实际只有四档字号 |
| 任务列表 | 可显示勾选状态，不是原生可操作任务 |
| 表格 | 支持GFM、对齐、横向滚动，不支持任意合并单元格或复杂多行表格 |
| 代码 | 支持围栏、复制、有限语言高亮；Mermaid尚无专门绘图分支 |
| 数学 | 识别LaTeX标记，但主要转成Unicode文本；复杂矩阵、分层分式和对齐不是真正公式排版 |
| 图片、音频、视频 | 走媒体组件；普通Markdown段内混排图片还有退化限制 |
| HTML/SVG/Canvas | 独立网页作品预览；不会把普通正文任意当脚本执行 |
| 来源/脚注 | 基础链接和引用式链接，不是完整的来源卡、脚注回跳系统 |

要统一体验，需要同时确定模型表达约定、消息类型和原生渲染规范，不能只改提示词。后续可优先评估复杂数学、Mermaid、来源引用等缺口，再由用户决定是否调整视觉。
