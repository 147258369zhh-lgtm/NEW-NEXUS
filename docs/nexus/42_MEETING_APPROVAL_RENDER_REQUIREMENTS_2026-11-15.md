## 3. 会议组合：12种真正不同的协作流程

### 3.1 当前缺在哪里

目前三种组合主要是在创建时预填角色，实际仍共用“主持规划 → 成员独立执行 → 主持汇总”。同屏显示大家的消息，不代表各Agent真的看得到别人的输出。

因此，新增用途必须改变真实调度和输入材料，不能只换几个名字。主持人负责协调，不默认冒充多个独立专家；模型内部思考不进入共享材料。

### 3.2 用途与阶段矩阵

以下角色是工作职责，可绑定你启用的自建或内置Agent；不强制指定某家模型。关键的独立对照应由不同参与者承担，人员不足时明确降级，不能虚构多方共识。

| 编号与用途 | 角色建议 | 真正执行阶段 | 谁能看谁 | 交付物与停止条件 |
| --- | --- | --- | --- | --- |
| M01 方案讨论 / 头脑风暴 | 主持、领域专家、反方或补充者 | 独立提案 → 公开讨论 → 定向回应分歧 → 主持归纳 | 首轮独立；后续看到已发布的公共发言 | 备选方案、取舍、未决问题；达到轮次或没有新分歧后停止，最终选择归用户 |
| M02 资料研究 / 文献调查 | 主持、分渠道收集者、证据核验者 | 拆研究问题 → 并行收集 → 去重归源 → 核验冲突 → 研究结论 | 收集时独立；核验者收到相关证据，其他人按阶段共享 | 带来源与日期的结论、矛盾证据和空白；关键问题覆盖或预算到达时结束 |

| M04 多模型竞答 / 事实核验 | 相互独立的答题者、核验者、主持 | 同题独答 → 对齐答案 → 找分歧 → 证据复核 | 首轮隐藏其他答案；比较阶段公开答案与依据 | 共识、分歧和可信依据；不能用多数票代替事实，证据不足明确保留 |

| M07 写作与审校 | 作者、结构编辑、事实审校、定稿者 | 提纲 → 草稿 → 结构修改 → 事实核验 → 定稿 | 草稿与修改意见按版本交接；不让不同人同时覆盖同一版本 | 定稿、引用和未核实内容；约定标准通过或修订预算到达 |

### 3.3 一套引擎承载这些用途

建议使用版本化的会议模板和通用阶段调度，不为12个场景各写一套运行器。

| 基础对象 | 必须保存的内容 | 作用 |
| --- | --- | --- |
| 会议模板 | templateId、version、用途、角色、阶段、默认预算 | 新建时固化版本；改模板不污染已经创建的会议 |
| 阶段 | stageId、前置依赖、输入引用、输出约束、并发、超时、失败处理 | 支持并行、顺序、互审、投票和返工 |
| 可见性规则 | 私有任务、公共板、定向交付、匿名聚合 | 真正控制每次模型输入，不靠提示词口头要求 |
| 成果与证据 | 产物ID、来源、版本、归属、引用许可 | 避免转发失效路径和未经授权的材料 |
| 执行检查点 | meetingRunId、stageId、attempt、状态、已提交输出 | 重启/取消/恢复时不盲目重跑已有副作用 |
| 结束规则 | 最大轮次、预算、验收标准、用户暂停与取消 | 明确何时完成、失败、部分完成或等待用户 |

先复用当前独立成员运行、角色授权、消息归属与汇总，再补阶段依赖、共享投影和恢复。初始并发宜保守，并受模型服务商、设备和单会议预算共同限制；具体默认值在实施时集中配置。

要防止“本轮未生成有效分工，没有启动执行”反复出现：

- 主持输出采用可校验的分工结构，角色用稳定ID，引用必须属于已启用参与者。
- 无效分工先做有限的一次格式修复；仍失败则明确报出未启动原因，不能假装执行。
- 只有预先允许且语义明确的模板可使用确定性的默认分工；不得随意把任务交给任意模型。
- 检查有效成员、工具权限、模型可用性、预算和阶段输入，再启动；一个成员失败不应抹掉其他成员成果。
- 调度事件、工具结果和终态归属原会议及原Run；切换查看其他记录不取消正在运行的会议。
- 旧会议保留原模板和上下文，不自动改成公开讨论，也不自动重新启动历史任务。

## 4. 运行模式与审批：采用Codex的分层思路

### 4.1 先把维度拆清楚

Codex式结构的关键是“怎样工作”“可以访问哪里”“谁来审批”分开。完全访问、请求批准、计划并不是同一维度的三选一。

本报告的Codex对照沿用第41号盘点对官方公开源码的固定版本核对，提交为`81b995a6c9a4c978f399775cfa5ce50702368749`。OpenAI官方文档站本轮再次访问仍返回403，不能据此声称已经核验当前桌面全部实验功能。以下学习机制是NEXA的扩展设计，不声称Codex已提供同样的长期学习能力。

| 维度 | 建议行为 | 与当前实现的差异 |
| --- | --- | --- |
| 普通执行 | 理解任务后在授权范围内持续执行，遇关键缺失信息再追问 | 保留普通会话能力 |
| 计划 | 调研、澄清、形成实施方案；允许可证明不实施修改的检查，不自动转执行 | 当前整类禁终端/MCP过粗，应按真实效果判定；未知效果不能冒充只读 |
| 目标 | 可在普通执行中建立持久目标，保存预算、完成条件、暂停恢复 | 不作为第三档权限；旧目标ID、预算和状态保留，不因迁移丢失 |
| 权限范围 | 项目/目录、设备、网络、账号、工具及效果范围 | 必须由执行层验证，不能只写提示词 |
| 审批人 | 需要审批时交给用户，或交给独立审查者 | 智能和手动不能继续走同一条固定门禁 |

计划模式不会因为“完全访问”而自动变成实施模式。测试/构建是否允许，要看它是否改动受保护的产物、项目或外部系统；不能仅凭名称叫“测试”就放行。

### 4.2 三种审批安排

| 安排 | 已允许范围内 | 需要额外范围或风险判断时 | 关键边界 |
| --- | --- | --- | --- |
| 完全访问 | 自动执行 | 用户授权任务内不再逐条弹产品审批；能力不可用则返回真实原因 | 不绕过系统/Root/网站验证，不替模型建立新的任务授权 |
| 智能审批 | 自动执行 | 独立审查者结合具体动作、范围和真实批准偏好，输出允许、询问用户或拒绝 | 审查者不能执行工具或自行签发权限；不确定、缺上下文或审查不可用时交用户 |
| 手动审批 | 自动执行 | 由用户批准所需的新增范围或动作 | 不是每次读取、每步点击都打断；一次授权的范围、次数和期限必须明确 |

你最新明确要求完全访问为全部权限。因此后续实现应同步更新旧规则、门禁、菜单说明与测试，不得保留旧版资金确认例外后仍声称“全部权限”。同时，模型不能通过应用设置工具将自己从智能/手动升级为完全访问。

已查到的优先修复点：

- 智能和手动当前通用门禁行为接近，尚没有真正独立的智能审查。
- 独立设置链对CONFIRM类型的处理有缺口；有条件允许模型未经确认改变审批模式。
- 当前全局设置会在后续工具调用时重新读取，一个会话放宽可能影响其他后台运行。
- “仅本地”的部分检查实际只是拒绝远端Agent，不等于验证真实用户来源，不能直接当信任证据。

建议每个新Run记录策略快照。撤销立即生效；放宽默认作用于新Run，正在运行的任务需要用户明确应用。成员实际权限取会议、阶段、角色、账号与资源授权的共同约束，不能靠会议模板扩大。

### 4.3 智能审批怎样学习

示例：你经常允许“同一项目内运行某个检查命令”，系统可以逐渐减少这类重复询问；它不能由此推出“允许所有终端、所有Root操作或向任意网站传文件”。

| 环节 | 实施规则 |
| --- | --- |
| 证据来源 | 只认执行层记录的真实用户点击批准、拒绝、撤销；模型回复、学习反馈工具、网页文字均不是授权 |
| 范围绑定 | 绑定工具原名、schema/效果版本、完整服务器身份与连接版本、账号、项目、目标范围和参数约束 |
| 候选形成 | 同类多次批准形成偏好候选；次数本身不等于无限授权，交由策略和独立审查评估 |
| 自动使用 | 仅匹配已验证的窄范围；参数、服务器、账号或效果变化则重新审查 |
| 拒绝与撤销 | 明确拒绝、撤销优先；超时和取消既不是允许，也不默认记为负偏好 |
| 管理 | 可查看依据、删除、暂停学习、设有效期；不跨账号、服务器和风险级别泛化 |
| 单次授权 | 执行前原子领取，防止两个并发调用重复消费同一个许可 |
| 审计 | 保存决策、依据、授权范围、最终执行结果，敏感值按需保护，不以删掉目标信息代替审查 |

建议数据链为`RunPolicySnapshot → ActionScope → ApprovalDecision → ApprovalGrant → ExecutionAudit`，长期偏好单独保存。

可复用现有CapabilityPolicy、ToolGrant、身份摘要、用户确认和学习仓库的部分机制；不能直接把设置授权仓库当通用授权库。尤其不能把模型可调用的`learning_feedback`记录成“用户批准过”。

## 5. 消息排版：让你自己调软件渲染器

内容结构由模型给出，最终字号、行高、代码块、表格与媒体布局由软件决定。增加用户设置即可，不必重新调用模型排版，也不必把整个聊天改成浏览器。

当前已有三类全局字体选择和整体界面缩放；新功能应补“消息排版”参数，不重复再建一套全局字体设置。

| 设置组 | 可调内容 | 建议行为 |
| --- | --- | --- |
| 预设 | 标准、紧凑、舒展、自定义 | 预设只改消息显示；可恢复默认 |
| 正文 | 字号、行高、段落间距 | 使用受限区间，兼容系统字体缩放和中文 |
| 标题 | 相对字号、字重、前后间距 | 层级保持一致，防止某档过大挤满屏幕 |
| 思考内容 | 字号、行高、默认折叠偏好 | 与正式回复分开，不影响模型真实输出 |
| 代码 | 字号、换行、横向滚动偏好 | 长代码可滚动，复制保留原文 |
| 表格 | 字号、行密度、横向滚动 | 不挤压成无法阅读的窄列 |
| 公式与引用 | 显示尺寸、公式横滚、脚注回跳 | 和正文统一缩放，链接可访问 |
| 查看方式 | 渲染结果 / 原始文本 | 用于看Markdown源文；切换不改历史数据 |
| 预览与保存 | 当前样例实时预览、恢复默认、备份迁移 | 两皮肤共享排版参数，皮肤只管材质与主题色 |

现有正文约16sp/26sp行高，思考约14sp/22sp；标题、代码、表格和块间距已有集中样式，可从这些所有者接入参数。历史消息按新参数重新显示，存储内容不被重写。复杂公式、脚注和合并表格属于渲染能力补全，不能靠增大字号解决。

字体使用已合法提供的系统字体或可合法分发的字体。不能仅因“像苹果”就把受限字体文件打进Android包。

## 6. 图片、音频、视频：统一来源与展示

### 6.1 图片

你的要求按以下方式落实：

- 上传图片、模型产物、Markdown图片共用图片组件，避免不同来源长得不一样。
- 小图在消息内容区左上对齐，保留原始比例；按设备像素密度合理显示，不把小图硬拉成大图或强行放中间。
- 大图先有界预览，展开后从左上开始按需查看，横向/纵向超出才显示对应滑轨；滚动查看不拖动整个页面。
- 不默认正方形裁切，不用背景色块填出一大块空白；有透明通道的图片保持透明。
- 超大图片按目标尺寸采样；支持区域解码时分块，不支持时使用受限预览并保留保存/外部打开入口。
- 加载、失败和重试都在原位置完成，不能先铺巨型空框导致消息跳动。

### 6.2 音频和视频

| 组件 | 展示内容 | 交互约束 |
| --- | --- | --- |
| 音频 | 紧凑播放条、文件名、播放/暂停、当前时长/总时长、进度 | 保存/分享作为次级操作；不把普通音频做成占屏大卡 |
| 视频 | 原比例首帧、播放、进度、静音、全屏 | 用户附件和模型产物用同一套控件；不显示黑色空块冒充首帧 |
| 通用文件 | 图标、文件名、类型/大小、打开/保存 | 不可解码或未知格式仍有可操作卡片，不白屏、不丢原文件 |

语音输入的悬浮球和消息中的音频播放器是两个用途；本轮媒体整改不顺带重做你已选定的语音球。

经典与液态玻璃使用相同的尺寸、层级、按钮顺序和状态，只读取各自主题材质。媒体小组件不另造一套玻璃，弹出层也沿用现有规范。

### 6.3 性能与能力边界

当前已有点播创建、单活跃音源、仅播放时约300ms更新进度、后台暂停和离开释放等机制，应保留并统一接入，避免重新写播放器。

需要补的是：

- 图片与视频首帧在后台线程解码，限并发、去重、缓存；可见时加载，离屏取消。
- 进度更新只刷新播放器局部，不重组整个聊天列表。
- 当前图片源大小上限12MiB、最长边3840、缓存16MiB，不等于总解码内存受控：3840×3840的ARGB像素仍可能约56MiB；需另设像素和并发内存预算。
- MIME、容器、编码和设备能力共同决定能否播放；识别AIFF或AVIF不等于该手机一定能解码。
- 文件分享用只读FileProvider URI，保存经SAF；附件不会因为被展示而自动解压、安装或执行。
- HTML作品沿用独立进程、来源归属及资源预算，不让聊天滚动时反复创建WebView。

## 8. 追问交互：在已有能力上补完整

### 8.1 当前可复用与真实缺口

已有`request_user_input`工具、单题单选、自由输入、显示前保存问题、唤醒前保存答案。持久问题从独立执行事件中读取，不仅依靠聊天正文，正文压缩不应直接丢问题。

但还存在：

- 选项只有字符串，缺稳定ID、描述、多选与多题模型。
- 活跃等待有超时，但持久问题没有完整deadline，重启后时效不够明确。
- 重启恢复可能拼成新一轮提示，未恢复原tool_result；消费标记与续答不在统一事务里。
- 全局取首个pending问题的入口不足以支持多会话和会议并发。
- 缺明确的decline语义及完整重复提交、过期、迟到答案处理。
- MCP遇到input_required目前直接返回不支持，不能只补一条能力声明就说完成。
- 远端A2A已有文本暂停续答等基础，结构化选项还没有贯通。

### 8.2 统一数据与操作

扩展现有工具，不并排造另一套ask_user。

| 层次 | 建议结构 |
| --- | --- |
| 请求信封 | requestId、runId、conversationId、toolCallId、source、目标参与者、真实回答者、schemaVersion、deadline |
| 多题内容 | questions数组；每题稳定id、single/multiple/text、必填、选项id/label/description、选择范围和输入限制 |
| 自由补充 | 独立other_text；不把用户补充混成某个显示标签或隐含权限 |
| 结果 | accept、decline、cancel、expired；内部过期状态按外部协议规则映射 |
| 持久恢复 | 回答与状态转换、续答outbox统一提交；原工具结果绑定原toolCallId |
| 并发 | 原子状态迁移与去重键，重复点提交不重复执行；旧问题不能覆盖新问题 |

建议多题分步展示，单题/多选共用现有规范的选项组件。切换会话或收起问题保持pending；明确取消才取消，不因关界面就误取消任务。提交校验不通过留在本题，不发半份结果。

运行器需在收到完整、可验证的提问调用后暂停依赖答案的工作，不能看到首个流式tool delta就粗暴终止响应。其他独立会话或会议成员仍可继续。

超时不代选，不等于同意；答题不产生权限授权。重启续答优先恢复原工具调用；无法做到时必须显式降级，不能盲目重放已发生副作用的工具。

### 8.3 两代MCP必须分开适配

| 协商协议 | 真实输入路径 | 实现重点 |
| --- | --- | --- |
| 2025-11-25兼容路径 | 服务端反向elicitation/create，客户端返回结果 | HTTP与stdio都需要反向请求分发、请求关联、超时取消、schema校验；能力声明必须与实际实现一致 |
| 2026-07-28项目最新路径 | MRTR：收到InputRequiredResult，包含inputRequests与requestState；收集回答后新RPC ID重试原请求 | 附inputResponses，原样回传不透明requestState；请求能力放在_meta.io.modelcontextprotocol/clientCapabilities；防止重复副作用和请求状态串用 |

版本必须按协商结果走，不能因为本地常量叫LATEST就假设所有服务端支持MRTR。旧版协议不支持的schema应明确拒绝或协商降级，不能悄悄改变字段含义。

2025-11-25及2026-07-28支持枚举多选数组；任意嵌套对象与任意对象数组仍不能照搬自有工具结构。适配层负责把统一内部问题投影到协议允许的结构。

普通邮箱等非秘密信息可以合法追问，不能像旧方案一样全部拦截。密码、密钥、token、付款凭据不进入普通表单；需要登录或验证的URL使用受控浏览器，校验来源与完成回调。追问表单不等于工具授权弹窗，两者可以共用视觉规范，不能共用授权语义。

## 9. 会话状态色：精确按你的四档规则

| 优先级 | 条件 | 颜色 | 边界解释 |
| --- | --- | --- | --- |
| 1 | 真正处于进行中的会话，包括后台仍运行 | 绿色 | 仅点开一条历史记录不自动算正在聊；进行中的等待用户/审批仍属于未结束会话 |
| 2 | 未进行，距最后真实会话活动不超过3天 | 橙色 | 正好3天仍为橙色 |
| 3 | 未进行，超过3天且不超过7天 | 红色 | 正好7天仍为红色 |
| 4 | 未进行，超过7天 | 灰色 | 8天及更久都为灰色 |

本报告把“正在聊”解释为存在未结束的实际运行；没有运行时，单纯选中历史记录仍按时间颜色。这样绿色表达真实进行中，选中表达你正在看哪条，两者不会混在一起。

时间使用最后真实消息或任务活动，不能让重命名、置顶、拖排序刷新颜色。若现有updatedAt混合了管理操作，需要补独立活动时间投影；从历史消息回填，未知时间不能伪装成“刚刚”。

新建尚无消息的会话，以创建时间作为首次时间基准。这里的3天、7天按经过的72小时、168小时计算，日期分组仍按当地日历显示，互不干扰。

当前实现是运行绿、其余在10天内逐渐变淡后灰，需替换成以上离散规则。不改排序、日期折叠、文件夹与置顶。此次只针对你明确说的会话，不擅自改变会议室已有失败/等待等语义色。

四档颜色共用两皮肤语义令牌，保留现有状态标记位置，不把整张卡染成大色块；没有持续闪动和光晕。刷新在进入前台、任务/消息状态变化和跨时间阈值时进行，不加高频轮询。
