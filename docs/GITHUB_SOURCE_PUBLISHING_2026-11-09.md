# GitHub 源码发布与仓库卫生说明

## 发布目的

2026-11-09 的发布把 Eta 4.10.4 的源码、资源、测试、原生库、构建配置、第三方声明和开发复盘同步到现有 GitHub 仓库。用户同时要求保留这两天的知识点、感悟、开发重点和需求记录，因此仓库新增总复盘文档，并引用已有的逐任务技术文档。

## 纳入仓库的内容

- app 目录中的 Kotlin、Compose、Manifest、资源、测试、原生运行时代码和构建配置。
- docs 目录中的架构、需求、逐任务实现、故障复盘、第三方声明和本总复盘。
- scripts 中可复现的构建、审计和测试脚本。
- Gradle wrapper、版本目录和根构建配置。
- LICENSE 与上游同步说明。

这些内容足以复现源码结构、编译应用和理解实现决策。

## 明确不纳入仓库的内容

仓库根目录混有真机测试生成的调试图、UI XML、logcat、运行时数据库、测试音频、备份包、APK、AAR 临时目录和设备内导出的文件。这些内容不作为源码提交，原因包括：

- 可能包含 API Key、Bearer Token、账号数据、聊天内容、设备标识、文件路径或应用私有数据库。
- 截图和 XML 体积大，且随时会被新真机测试覆盖，不适合作为长期源码历史。
- 测试备份、音频和 APK 是构建或运行产物，应由 Release 页面或独立制品存储管理。
- 临时 AAR、build 输出与缓存会降低仓库可维护性，并可能违反依赖分发条件。

运行产物和真机证据应在脱敏后单独存放，并明确保留期限。敏感凭据、签名文件和本地配置永远不应提交。

## 提交前检查

发布前对 app、docs、scripts 和根构建文件检查以下模式：

- 常见 API Key 前缀、Bearer Token 和私钥头。
- 明文密码、OAuth secret、Webhook secret 和 MCP 认证信息。
- Windows 用户主目录、设备序列号和完整私有文件路径。
- 数据库、备份包、音频、截图、XML 和 APK 等运行产物。
- 过大的二进制文件与意外生成的原生构建缓存。

示例值、占位符、测试密钥名称和说明文字可以保留；真实凭据必须删除或改为用户配置项。

## Git 发布流程

本次采用选择性暂存，不使用 git add -A。先暂存明确的源码、文档与构建目录，再检查 staged diff、空白错误、敏感信息和改动规模。通过后创建一条描述 v4.10.4 与开发归档的提交，并推送到现有 origin/main。

推送完成后核对本地 HEAD、origin/main、GitHub 提交 URL 和两个复盘文档的相对路径。如果认证失败，保留本地提交，修复 GitHub 凭据后再推送；不创建未经授权的替代仓库。

## 长期建议

1. 在 .gitignore 中持续维护截图、XML、日志、数据库、音频、APK、备份和 AAR 临时目录规则。
2. 真机日志只上传脱敏后的最小片段，并保存复现步骤。
3. 大模型、语音模型和外部包通过校验清单与来源链接管理，避免把超大制品塞进主仓库。
4. 第三方许可证、源码来源和修改说明与相关代码同一提交更新。
5. 每次发布同时记录 commit、versionCode、APK SHA-256、验证项和未验证边界。
