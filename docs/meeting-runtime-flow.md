# 会议室运行流程

Eta 会议室采用“主持人监督器 + Agent 作为工具”的受控拓扑。用户与所有参与者共享一条可持久化会议记录，但每个参与者只获得自己的独立模型上下文。

## 一轮消息如何执行

1. 用户提交文本后，`MeetingRunCoordinator` 先做单房间准入并申请前台执行租约。同一会议已有运行时，新消息不会重复进入。
2. `MeetingMentionRouter` 解析 `@`：
   - `@` 一个 Agent：该 Agent 直接执行。
   - `@` 多个 Agent：各任务并行执行，彼此不读取对方的中间结果。
   - 未 `@`：主持人从可用名册中选择 1 至并行上限内的参与者；选择失败时可按设置回退到全部已启用 Agent。
3. 当前用户消息先写入会议记录，随后每个目标创建持久化 `meeting_task`，并原子切换到运行状态。
4. 每个参与者收到独立任务指令。它的历史只包含此前的用户请求、自己的历史结果和主持人历史汇总；其他 Agent 的独立结果不会进入该参与者的上下文，避免相互污染。
5. 参与者完成后写回一条 Agent 消息及结果消息 ID。失败或取消会写回任务状态和系统消息，不覆盖已经完成的其他参与者结果。
6. 主持人接收本轮全部成功结果，生成汇总。关闭自动汇总时，本轮保留各 Agent 的独立结果并等待用户指定下一轮。
7. 会议恢复到等待用户状态；用户可继续 `@` 特定参与者，或让主持人重新分派。

## 上下文与压缩

参与者跨轮历史由 `MeetingContextHistory` 构造，按时间顺序发送给现有 `AgentModelClient`。当前用户请求只作为新 prompt 发送，历史快照在写入当前消息之前取得，因此不会重复。

正常对话和会议室都使用 `AgentContextSession` / `AgentContextCompactor`。触发条件包括达到模型上下文预算、请求返回 `CONTEXT_OVERFLOW`，以及显式强制压缩。自动压缩必须同时满足全局开关和会议室独立开关；最终摘要先持久化，成功后才替换模型上下文，原始 transcript 继续保留。

## 状态和恢复

- 房间任务以 `queued`、`running`、`completed`、`failed`、`cancelled` 持久化。
- 离开 Compose 页面不会取消会议轮次；取消、返回键或前台执行租约终止才会停止运行。
- 进程死亡后不会自动重放可能已经产生副作用的参与者任务。启动恢复会将未完成任务标记为失败，并要求用户检查已有结果后明确重试。
- 单次模型或 A2A 请求受会议室超时设置约束。超时、连接断开、后台运行和运行中任务可在仅 Debug 构建显示的“调试诊断”卡片中查看计数与最近事件。

## 主持人边界

主持人负责选择参与者和汇总，不直接代替参与者执行专业任务。主持人自己的历史上下文也使用同一构建规则，因此跨轮会议摘要可以持续积累；被停用或移除的主持人不会继续被调用。
