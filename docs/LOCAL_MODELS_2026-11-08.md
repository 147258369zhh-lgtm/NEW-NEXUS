# 本地模型 4.9.2：内置运行时、稳定性和兼容格式

入口位于“模型提供商 → 本地模型”。4.9.2 已内置三个真实的端侧推理引擎，下载或导入后不需要填写 API 地址，也不需要另装 Ollama、LM Studio 或 llama.cpp。

## 当前可直接对话的格式

| 格式 | 内置引擎 | 当前能力 |
| --- | --- | --- |
| `.litertlm` | LiteRT-LM 0.19.1 | CPU / GPU、流式生成、停止、多轮上下文、真实预热 |
| `.gguf` | IRIDIS 2.4.5 的 llama.cpp arm64 运行时 | CPU / OpenCL、流式生成、取消、上下文回退、加载进度 |
| MNN 文件夹 / `.zip` | IRIDIS 2.4.5 的 MNN arm64 运行时 | CPU / OpenCL、流式生成、取消、上下文回退、目录完整性校验 |

`.task`、`.onnx`、`.tflite`、`.litert`、`.safetensors`、`.bin`、`.pt`、`.pth` 仅可先保存到模型库。它们分别需要完整目录、专用运行时、转换流程或专项模型适配，不会在界面中伪装成可以聊天。

MNN 必须以包含 `config.json` 与 `llm.mnn` 的完整目录或压缩包导入，不能把其中单个权重文件当成完整模型。ONNX GenAI、ExecuTorch 等其余模型包仍需后续专用适配。

## 借鉴 IRIDIS 的范围

- 直接复用其 Apache-2.0 arm64 `libiris_llama.so`、`libiris_mnn.so` 和稳定的 native/JNI 表面，避免在手机上重复实现底层算子、OpenCL 初始化与模型加载器。
- 借鉴单实例模型持有、加载阶段反馈、CPU 亲和/性能线程提示、GPU 失败回退、一次 token 预热、取消与空闲卸载的设计。
- 没有照搬 IRIDIS 的应用壳、文件选择流程和页面布局；Eta 保留统一的本地模型概览、模型管理、高级参数与能力中心视觉语言。
- 新增统一的 WorkManager 下载、断点续传、大小与 SHA-256 校验、Provider 自动路由、全局模型选择、原生崩溃熔断、低内存降级，以及普通会话、会议室和子 Agent 的接入。

## Qwen3 0.6B 闪退修复

真机 tombstone 显示正式包在 `LiteRtLmJni.nativeCreateConversation` 中以 `JNI DETECTED ERROR IN APPLICATION: mid == null` 触发 `SIGABRT`。LiteRT-LM 0.19.1 的 AAR 没有提供完整的 consumer R8 规则，发布构建把 JNI 所读取的 `SamplerConfig`、`ThinkingConfig` 和 `ConversationConfig` getter 删除或改名。

4.9.2 使用完整的 LiteRT-LM JNI 保留规则，并在发布后检查 mapping 和 APK 内 JNI 表面。此类规则不能缩成几个 benchmark 方法，否则编译仍会成功，但首次创建会话会让整个应用进程中止。

4.9.2 同时修正了三个导致“已下载但无法启动”的问题：LiteRT-LM 不再把映射权重按 2.2 倍重复估算，不再把全部输出预算预先占满小上下文，内存计划缩短上下文后也不会在每次请求时误触发重载。GGUF/MNN 的温度、Top-K、Top-P、最大输出和 thinking 设置可在下一条消息生效；只有后端、线程和上下文变化才会重载原生引擎。

界面将外部 Ollama、LM Studio、llama.cpp 服务从模型提供商首页移除，收进“本地模型 → 运行 → 外部服务”。内置 GGUF/MNN/LiteRT-LM 仍从同一概览页一键下载并启动，不要求用户再填写 API 地址。

启动验证不再以“Engine 对象创建成功”为通过标准。LiteRT-LM 和 GGUF 都必须创建真实会话并生成至少一个 token，随后才会把模型设为全局模型。

## 原生崩溃隔离与内存保护

- 进入 JNI 前同步写入模型 SHA-256、运行库版本、CPU/GPU 后端和执行阶段。
- 下次启动通过 `ApplicationExitInfo.REASON_CRASH_NATIVE` 判断上一次是否真正发生原生崩溃，Kotlin 异常不会被误判成原生崩溃。
- GPU 发生原生崩溃后，同一模型后续优先回退 CPU。
- 同一模型、后端和运行库连续两次原生崩溃后，停止无人值守的自动重试；用户仍可手动换 CPU、缩短上下文或更换模型。
- 只有完整原生回合成功结束才解除警戒。首个 token 后、生成途中发生进程崩溃同样会在下次启动被识别。
- 加载前按模型文件、上下文窗口和引擎估算工作集，预留 512 MiB 系统余量；空间不足时先缩短上下文，仍不足则给出明确错误并拒绝加载。
- `onTrimMemory` / `onLowMemory` 会释放空闲模型。正在生成的句柄不会被强制回收，避免同一原生对象被并发释放。

## 一键下载和启动

- 推荐模型直接显示文件大小、许可、引擎、格式和能力。
- “下载并启动”会依次完成下载、大小校验、SHA-256 校验、文件头校验、内置运行时注册、真实预热和全局模型选择。
- 已安装模型在概览页直接显示“立即启动”；运行中的模型显示“停止”。导入 MNN 文件夹或压缩包时，文件校验、注册和启动共用同一流程。
- 下载通过 WorkManager 执行，使用 data-sync 前台通知；支持 HTTP Range 续传、取消、失败状态和退避重试。
- 下载地址可修改并持久化，也可恢复推荐地址。推荐源使用国内可访问的 ModelScope。
- 若“下载后加载”和“下次打开 Eta 时恢复当前选中的本地模型”同时开启，应用重启后会只恢复当前选中的内置模型；不会恢复失败或未选中的模型。

## 默认模型建议

- Find X7 Ultra / SM8650 / 16 GB：Qwen3 0.6B LiteRT-LM、Qwen2.5 0.5B GGUF、Gemma 3 1B LiteRT-LM 适合作为默认档位。
- Gemma 4 E2B 体积约 2.4 GiB，适合愿意使用更多内存和存储的用户；当前只暴露已验证的文本能力。
- 1B 到 2B 模型可以作为质量档；4B 以上模型必须结合可用内存、上下文长度、温度和电池状态使用。
- 当前只打包 `arm64-v8a`。GGUF 原生库优先使用 ARMv8.2 的 dot-product、i8mm 和 fp16 指令；不满足时会明确提示无法加载，不会静默崩溃。

## 设备策略

应用会读取 SoC、RAM、可用存储、电量、省电状态和 Android Thermal API，并在页面回到前台、温度等级变化或省电模式切换时重新计算建议：

- Find X7 Ultra 默认建议 4 个 CPU 推理线程和 8K 上下文；高温、省电或更严格的内存状态会降到 4K/2K。
- 其他设备按总 RAM 分档：12 GB 以上最高 8K，8 GB/6 GB 为 4K，低于 6 GB 为 2K。
- GGUF 初始使用 CPU 基线，也可选择 OpenCL GPU；GPU 失败且尚未输出 token 时自动回退 CPU。
- 省电策略、温度策略、空闲卸载、后端、线程、上下文、最大输出、采样参数和思考开关都在高级页统一管理。

## Android 16 / 17 兼容

- 目标 API 37，最低 API 33。
- Release 构建关闭 `debuggable`，避免 ColorOS 把调试标志与无障碍服务关联为风险。
- APK 仅包含 16 KiB 页对齐的 arm64 原生库。
- 正式包必须验证签名、非 Debuggable、原生库存在、R8 mapping 保留 JNI 类和 getter，以及 WorkManager 的反射构造器。

## 隐私与备份

- 模型文件保存在应用私有目录，不会上传给在线模型服务。
- 普通 JSON/完整数据备份不包含大模型文件，避免备份体积失控；模型索引可在恢复后重新定位或重新下载。
- 本地对话是否离开设备只取决于当前选中的运行时。内置 LiteRT-LM、GGUF 和 MNN 在应用进程内执行。

## 当前边界

- 内置本地模型当前稳定开放文本对话；工具调用桥、图片输入和语音模型尚未接入，界面不会把未验证能力标成可用。
- Gemma 4 E2B 等大模型能否运行取决于具体机型内存、系统回收策略和温度状态；预热失败不会覆盖原来的在线模型。
- 用户自定义下载地址与“模型文件导入”都保留；Ollama、LM Studio 和 llama.cpp 服务放在“高级 → 外部本地服务”，用于没有内置引擎可用的模型包，不与内置运行时混为同一流程。
