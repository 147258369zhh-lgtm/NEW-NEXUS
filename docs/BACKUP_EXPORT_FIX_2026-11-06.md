# 备份导出卡住修复

日期：2026-11-06。接续工作区搜索与 ZIP 导出之后的第三批开发。用户报告：选择位置后持续十几分钟没有结果，加密和明文均出现；真机测试由用户负责。

## 已发现并处理的问题

1. 原文件收集使用 `walkTopDown().filter(File::isFile).toList()`，先递归枚举、排序全部文件，再开始归档。目录链接会被跟随，PRoot 文件树中的环、guest 绝对链接及大量文件可导致反复扫描或长时间无反馈。改为 NIO 不跟随链接的流式遍历，在遍历过程中检查取消和条目/深度预算。Linux 环境仍纳入归档；链接保存在新清单中，不通过删除环境来绕过问题。
2. 原加密流每次 `write` 都创建独立 GCM 帧，包括 ZIP 头的单字节写入。已用 4096 次单字节写入的回归测试复现明显膨胀，旧实现断言失败。改为 1 MiB 分帧缓冲，保留原加密容器和旧帧读取兼容性。
3. 原 ZIP 直接写系统文档，未缓冲的小写入对本地/云端文档提供方均可能造成严重开销，且打开输出流发生在主线程。现在先在缓存中完整生成，以快速压缩和缓冲写入，随后在 IO 线程复制到文档，关闭成功才报告完成。
4. 原页面只有“处理中”，没有进度或取消。新增阶段、文件数、原始内容大小、复制进度、取消入口与持久显示的结果/错误。密码改为在文件选择器返回后确认，不保存在页面重建状态中。
5. 严格清理测试还暴露了检查/导入归档时内部 JSON 输入流未关闭的问题，已修正；没有通过忽略 Windows 文件锁错误来掩盖泄漏。

这些是源码与自动测试确认的问题及修复，不代表已经定位到用户设备上的唯一原因。新页面的阶段与计数也可用于进一步确认设备上的阻塞位置。

## 格式与兼容

完整清单升级到 schema 3，新增空目录、符号链接及普通 POSIX 权限。链接不会在校验阶段被实际创建；完成校验和文件替换后才恢复链接和权限，清理及回滚均不跟随链接。旧 JSON、schema 1/2 和旧加密帧继续可读。旧版应用不能读取 schema 3，需要先更新接收设备。

导出限制、取消和系统文档复制的具体边界见 [备份格式说明](backup-v5.md)。准备失败保留已有目标，最终复制失败或取消仍可能留下部分文件。未进行 Android 真机安装、真实凭据跨设备恢复或 PRoot 环境端到端恢复测试。
