# Eta 开发复盘：2026-11-06 至 2026-11-09

## 1. 这份记录的范围

这份文档把四天里最重要的技术判断、实现重点、踩坑过程、用户要求和验证边界集中在一起。逐任务的详细证据仍保留在 docs 目录中，本文件负责说明为什么这样设计、哪些能力已经落地、哪些只是在规划中，以及后续开发最需要警惕什么。

本轮工作的目标不是增加几个孤立的设置页，而是把 Eta 从“能聊天的移动端应用”推进到“能积累经验、调用能力、执行任务、感知环境并恢复上下文的 Android Agent 平台”。所有发布记录都必须区分真实实现、基础框架和未完成能力，不能把界面入口当成功能完成。

## 3. 四天时间线

### 2026-11-06：平台地基、无障碍与数据安全

这一天先解决应用能不能持续工作的问题。无障碍授权在 ColorOS 上出现授予后很快失效，普通会话和会议室又会把 runtime 失败直接暴露给用户。修复重点包括前台服务存活、无障碍服务健康检查、权限状态真实性、入口状态恢复和 Release 包调试标志。Release 版本必须保持 android:debuggable=false，否则侧载设备会把无障碍服务视为高风险。

文件与项目工作区开始形成统一入口。项目文件夹、会话绑定、产物索引和右侧文件区不是四套独立功能，而是同一套工作区身份。文件分享、导入、选择目录和长期保存也统一走 Android Storage Access Framework，避免依赖不可移植的绝对路径。

备份是第一轮数据可靠性的重点。旧流程把大量数据一次性序列化，超大对象、目录授权、密码保护和恢复进度都可能让界面长期无反馈。新的方向是流式归档、版本校验、选择性内容、分阶段进度和原子恢复。只要有一个阶段没有真实完成，就不能显示“导出成功”或“恢复完成”。

### 2026-11-07：Agent Runtime、记忆、Skill 与自动任务

普通会话和会议室最常见的故障来自请求协议而不是模型本身。HTTP 400 invalid_request_error 通常意味着消息顺序、空内容、工具结果角色、重复 tool call id、图片格式或 provider 不接受的参数。处理原则是先构造合法、最小、可验证的请求，再做协议适配，不能靠每个 provider 各自猜测。

工具调用链被拆成目标、候选工具、权限判断、参数校验、执行、结果回传和错误恢复。Agent 不应该看到所有工具，也不应该在权限不足时假装执行成功。普通会话、会议室和子 Agent 必须复用同一套工具目录和敏感操作策略，同时保留各自的任务上下文。

记忆系统从“保存聊天摘要”升级为分层模型。长期事实、项目记忆、任务状态、未确认候选和原始来源各自有生命周期。自动提取只产生候选，经过去重、冲突识别、作用域判断和用户确认后才进入稳定记忆。记忆可以搜索和注入，但不能无界增长，也不能让旧事实覆盖被明确修正的新事实。

记忆和自学习合并体验后，最重要的不是减少一个入口，而是让用户看懂数据从哪里来、属于哪个项目、为什么被保留、下一步会不会影响 Agent。文档查看、返回栈和筛选必须稳定，不能让用户进入一个页面后无法回来。

定时任务从单一时钟触发器开始扩展为触发、工作流、执行记录和恢复机制。真正可靠的后台任务需要 WorkManager、幂等键、超时、重试、并发限制、执行结果和重启恢复，单纯保存一条配置并不能算完成任务。

### 2026-11-08：能力中心、本地模型、语音与提示词注入

能力中心成为新的界面基准。它强调清晰层级、轻量卡片、克制的底色、稳定的排版、状态与操作分离、紧凑但可点按的控件，以及二级设置按需展开。后续的记忆、子 Agent、模型提供商、MCP、自动任务和备份都向这套设计语言收敛。

Skill、MCP、API Connector 和本地工具需要统一发现与治理，但协议不能混为一谈。Skill 更像带说明、脚本和资源的可复用工作方法；MCP 是标准工具服务协议；API Connector 是面向具体服务的接口封装。统一的是能力目录、权限、来源、状态和调用记录，底层协议仍保持清晰边界。

本地模型开始搭建完整基础设施：文件来源可改、本地导入、下载校验、模型清单、运行时状态、CPU/GPU/NPU 路由、回退、上下文字段、流式输出、停止和崩溃隔离。对手机来说，模型能否加载只是第一步，更要处理内存压力、热状态、后台策略、架构兼容、模型格式和异常卸载。LiteRT-LM、GGUF、MNN 以及语音与视觉模型不能只塞进同一个“聊天模型”列表，能力类型必须分开。

语音系统开始处理 ASR、TTS、录音、播放、打断和音频租约。全双工的难点不只是同时存在两个组件，而是麦克风与扬声器资源、回声、模型并发、录音生命周期、停止时的竞态和前台服务存活。优先级应保证主文本模型，其次语音识别，最后语音合成；任何停止失败都要能超时回收。

提示词注入被做成“固定策略层”，而不是散落在用户消息里的临时文本。需要明确作用范围，包括全局、普通会话、会议室、子 Agent 和指定模型，还要支持从互联网导入常见模板与导出文件再导入。提示词能约束行为，但权限由工具策略执行，不能让提示词绕过硬边界。

### 2026-11-09：虚拟屏、故障收口与 v4.10.4

虚拟屏稳定性继续增强。重点是创建、切换、关闭和进程死亡的恢复，不让单张卡片或一次转场错误卡住整个 GUI 操作。多实例能力仍需要单独的显示、输入、生命周期和资源预算设计，不能简单用多个截图循环冒充多开。

本轮最后集中修复了多图预算、上下文压缩、通知、搜索、文件编辑冲突、状态真实性和重复 checkpoint。将版本推进到 4.10.4，versionCode 2026110902，targetSdk 37。Release 包通过编译，签名与可调试标志检查完成；文件编辑、会话存储、网页搜索和权限检查做了定向验证。这不等同于完成 Android 16/17 全量真机回归。

## 4. 知识点与工程判断

### Android 与系统能力

Android 16/17 和 ColorOS 17 的后台、麦克风、通知、无障碍、文件选择和厂商省电策略必须按真实设备适配。应用能申请某项权限，不代表后台能长期保留；服务处于 enabled 状态，也不代表系统仍能稳定投递事件。健康检查要读取权威状态，修复动作要可解释，失败时给用户可执行的下一步。

Root 可以扩大能力，但不能成为唯一前提。无 Root 时仍有无障碍、SAF、通知监听、前台服务和用户确认路径。LSPosed 不作为基础依赖，因为用户明确不使用，而且它增加版本兼容与信任成本。最大权限的目标应通过公开系统 API、专用授权和清晰的操作记录实现。

### Agent Runtime

Agent 的可靠性来自状态机，而不是一个大循环。运行需要稳定 run id、事件序列、消息持久化、工具调用配对、取消、超时、重试、断线恢复和最终状态投影。会话 UI 必须能在进程恢复后重建同一结果，不能靠聊天页面的临时列表。

Provider 适配需要区分能力。OpenAI Chat Completions、Responses、Anthropic Messages 和 Gemini 对 system 消息、工具 schema、图片、reasoning、stream finish、缓存和 usage 的规则不同。请求参数只发送模型声明支持的字段，错误信息要保存诊断上下文，但不能泄露 API Key。

### 上下文与成本

上下文窗口、最大输出、压缩阈值和模型真实能力是四个不同参数。手动压缩需要选择消息范围、生成结构化摘要、保留工具状态和用户约束，再原子替换上下文。自动压缩按 provider 实际 usage 判断，不做无依据的 token 估算。图片按预算缩放和编码，避免同一截图重复发送。

成本与轨迹记录应保存请求所用模型、输入输出用量、缓存命中、耗时、重试、工具调用、压缩和终止原因。统计不能只展示一张漂亮图，必须能下钻到一次运行，帮助定位慢在哪里、贵在哪里、为什么失败。

### 记忆与 Skill

主流 Agent 记忆通常至少分为工作上下文、会话记忆、项目或任务记忆、长期偏好和外部知识。Eta 采用分层与作用域结合的方式：不是把所有内容写成一个摘要，而是让每层有独立检索和淘汰规则。

记忆到 Skill 不能自动封闭。合适流程是：任务执行记录、重复模式检测、候选提炼、来源与适用范围、成功证据、离线或试运行验证、用户确认、版本化发布、调用反馈和淘汰。一次性操作、错误经验、敏感资料和缺乏验证的流程不能直接成为正式 Skill。

### 自动任务

自动任务的价值来自“条件可靠、动作可验证、失败可恢复”。时间只是最基础的触发。设备连接、位置、电量、文件变化、任务完成、系统启动、语音和手动调用可以逐步接入，但每个触发器都要有权限、精度、耗电、重复抑制和隐私说明。流程编排还需支持条件分支、等待、重试、超时、通知和人工确认。

### 本地模型与语音

本地推理是资源调度问题。模型格式决定运行时，模型能力决定入口，设备后端决定性能，内存和温度决定稳定性。一个模型失败时回退 CPU 是合理策略，但自动回退不能掩盖不兼容或文件损坏。卸载必须经过可超时的状态机，即使原生线程卡住也要让 UI 进入可恢复状态。

ASR 和 TTS 要作为独立能力接入 Agent，而不是伪装成聊天模型。音频全双工还需要考虑半双工基线、可打断播报、录音与播放并发、回声消除、静音检测、前后台切换和崩溃后的设备释放。

### 备份与恢复

备份的首要目标是可验证恢复。格式里要有 schema 版本、导出时间、应用版本、内容清单、校验信息和可选加密参数。导出使用流式写入和分阶段进度；导入先验证，再临时恢复，最后原子替换。选择部分内容时也要维护数据库关联，不能只恢复一半表或恢复悬空文件索引。导入进度必须来自导入任务，不能复用导出状态。

### UI 原则

精致不是加更多渐变和说明文字。界面应减少重复入口和口号式描述，保持统一的间距、字号、圆角、图标语义和颜色层级。主状态和高风险操作分开，低频参数进入二级页，按钮使用短动词，禁用态解释原因。能力中心是当前基准，后续模块要复用设计令牌与现有组件，而不是每个页面重新发明一套布局。

## 5. 用户明确要求

这些要求直接影响后续设计和验收：

1. 所有 UI 必须精细、雅致、协调，图标、字体、间距、层级、底色、按钮和状态反馈都要认真处理，基准是能力中心与会议室。
2. Android 16、Android 17 和 ColorOS 17 都要有良好兼容性；OPPO Find X7 Ultra 是当前重点真机，不允许 LSPosed 成为依赖。
3. 普通会话、会议室和子 Agent 都必须真实调用工具，权限状态必须可信，不能修好一个入口又破坏另一个入口。
4. 记忆要分层，自动提取、去重、冲突确认、项目作用域、文档查看和返回导航都要可靠。
5. 记忆要可持续转化为 Skill，但一次性经验和未验证内容不能自动固化。
6. 自动任务要比简单定时器完整，覆盖多种触发条件、流程步骤、历史、重试、暂停和恢复。
7. Skill、MCP、API Connector 和本地工具要有统一能力中心，同时保留协议差异和权限边界。
8. 本地模型要能下载、导入、一键启动、流式运行并进入会话、会议室和子 Agent；语音、视觉和向量模型要按能力分类。
9. 本地推理要针对手机优化，支持 CPU/GPU/NPU 选择、失败回退、状态信号和性能指标。
10. 语音识别、合成和播放要能接入对话，逐步支持可打断的双工交互。
11. 提示词注入要支持全局、指定会话、会议室、子 Agent 和模型范围，并支持通用模板导入导出。
12. 数据备份必须能够成功导入；自动备份可配置时间、目录、内容范围、格式、密码和保留份数。
13. 运行轨迹、成本统计和 Agent 指标要真实、可下钻，不能只有演示页面。
14. 临屏与虚拟屏要稳定、可恢复，后续再评估多实例和更强 GUI Agent 能力。
15. 功能不能只做入口和配置，必须有真实运行链路。
16. 任何参考项目都只用于学习和合理复用，目标必须达到或超过参考能力，并清楚标注未完成部分。

## 7. 开发感悟

第一，用户看到的“小故障”经常是整条链路的末端。Runtime 失败可能来自权限、消息格式、Provider 参数、工具结果、状态恢复或 UI 投影；必须沿链路找第一个错误，而不是在最后一段反复重试。

第二，自动化和 Agent 的风险不在模型会不会说，而在它是否知道工具边界、何时停、失败后是否可恢复。结果状态必须由真实执行证据生成。

第三，本地模型、语音和虚拟屏都比普通设置更依赖资源生命周期。没有超时、幂等和回滚，功能越强，卡死范围越大。

第四，UI 质量是工程质量的显影。一个按钮过大、状态颜色不明确、二级弹窗盖在背后或返回栈断裂，往往说明状态模型没有设计清楚。先修信息架构，再调视觉细节。

第五，文档要帮助下一位开发者做决策。只写“已完成”没有价值，必须写清接口、数据迁移、失败边界、验证方式和剩余工作。

## 8. 后续开发顺序

建议按以下顺序推进，避免再一次故障蔓延：

1. 先做 Android 16/17、ColorOS 17 的 Release 真机回归，覆盖无障碍授权、后台麦克风、SAF、通知、重启恢复和模型加载。
2. 统一 Agent 请求与工具调用的契约测试，覆盖普通会话、会议室、子 Agent、MCP、Skill 和本地模型。
3. 完成备份全链路真机验收：自动备份、选择内容、密码、导出、导入校验、部分恢复、失败回滚和版本升级恢复。
4. 完成本地文本模型与语音模型的资源调度、同时运行、超时卸载、CPU 回退和性能指标。
5. 深化记忆候选、冲突确认、项目作用域和记忆到 Skill 的验证闭环。
6. 扩展自动任务触发器和可视化编排，但每个触发器都要有真实调度与日志。
7. 完成 API Connector 的授权、调用、错误恢复和凭据保护闭环。
8. 完成能力中心各页面的细粒度 UI 审计和无障碍检查。

后续任何提交都应继续说明“实现了什么、怎么验证、仍缺什么”，并保持源码、测试、第三方声明和开发复盘同步更新。
