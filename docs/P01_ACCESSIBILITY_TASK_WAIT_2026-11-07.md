# P01.2 无障碍断线与任务恢复等待

接续独立 Root 恢复和连接健康检测，完成 Runtime 任务在服务失联时的等待路径。普通模式和 Root 增强共用此执行边界；不会要求 LSPosed。

## 实际执行变化

旧路径在 `AgentLocalTools.executeLocal` 的 GUI action 内调用恢复，等待时保留操作权。新路径先检查参数、Root 和当前工具权限，在取得 action 之前进入 `AccessibilityRunGate`。真正执行前仍重新检查权限与连接；这一层只做短检查，不再次长等。

- 每个 run 共用累计五分钟等待预算，多个成员/子任务调用同一执行器时不会各自重新开始计时。预算用尽返回 `ACCESSIBILITY_WAIT_TIMEOUT`，连接仍未恢复时后续调用立即结束等待。
- 恢复请求每次断线最多一次；独立 Root helper 与已有保护后端继续按已启用设置、Root 能力和有限退避决定是否请求恢复。预算不足以容纳后端上限时只等待手动恢复。后端失败仍可在系统设置恢复，不进入无限写设置循环。
- 等待释放本 run 旧所有权，同时持有全局无障碍干预 token。其他 run、会议成员和子任务不能在用户打开系统设置时抢屏；已开始的原子动作先结束，再进入恢复引导。
- token 在恢复、超时、取消、异常时释放；多个干预同时存在时不会因其中一个结束而解封其他干预。用户手动暂停是独立状态，自动恢复不会替用户点继续。
- 停止会唤醒睡眠/排队并中断阻塞恢复 helper，执行前再检查取消，不自动重放待执行操作。
- 恢复后的点击/输入等写操作返回 `ACCESSIBILITY_RESTORED_REOBSERVE`，本次没有执行。旧节点、坐标与观察被清除；先 `observe_screen` 再决策。即使服务在两个工具之间短暂断线后已经自动重连，也通过断线代次使旧观察失效。
- 观察过程中断线不发布旧节点/图片。已成功动作的后续观察失效会保留动作成功状态，并要求重新观察，避免把后续失败当成整个动作失败而诱发重放。

## 状态、会议和 UI

`AccessibilityWaiting` 事件通过 IPC、运行归档、检查点与统计轨迹传递等待/恢复/超时/结束阶段，采用稳定 phase 码。活动连接回放仍显示活动等待；磁盘重启恢复将等待转换成结束，不能重新建立已经不存在的活动运行。结果先于终态事件到达时也清除等待卡，只结束所属 run 的状态。

主聊天等待卡接到现有“权限健康”和“停止任务”；语音浮层共用卡片并接停止入口，没有健康导航时可打开系统无障碍设置。设置入口失败显示可理解的错误。操作行能换行、最小高度 48dp；颜色、圆角、留白与字重沿用现有 Miuix/皮肤 token，说明不固定高度，资源覆盖英/简/繁。

胶囊/通知有明确“等待无障碍恢复”状态。会议 Runtime 不再丢弃这类事件，主线程 Messenger 回调只投递到串行 IO 记录器，结束时先冲刷阶段并清理，不阻塞界面：在原会议消息位置更新对应成员的阶段，并保存事件；重复回放不会把已结束阶段改回等待。会议取消/结束或进程恢复会结束等待，不重复执行原任务；删除后的延迟事件不会复活会议。会议使用既有系统消息和停止控件，完整共享消息主体继续由 P02.1 完成。

## 用户真机验证步骤

1. 普通模式运行一个需要观察/点击的任务，在系统设置暂时关掉 Eta 无障碍。确认任务显示等待，没有继续点击；其他运行也不应抢系统设置页面。
2. 五分钟内重新打开服务。观察会重新读取当前页面，旧点击/输入没有重放；让 Agent 按当前页面继续。
3. 等待时停止任务，确认立即结束；未恢复服务时继续运行其他后台文件/网络任务不触发 Root 或反复恢复。
4. 保持服务失联直至等待超时，确认出现明确状态，重复 GUI 工具不再重新等待五分钟。
5. 手动暂停另一个屏幕运行，再恢复无障碍，确认手动暂停仍保留。
6. 同一会议安排两个可操作屏幕的成员，关闭/恢复服务及停止会议，确认能定位对应成员、等待阶段只更新原位置，取消/重启不自动重放。
7. 开启独立 Root 恢复重复上述流程，再撤回 Root，检查仍有普通模式恢复入口；无需 LSPosed。升级 Android17/ColorOS17 后重复。
